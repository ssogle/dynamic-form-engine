# Testing Strategy & Harness Governance Rule

당신은 높은 신뢰성의 엔지니어링 하네스를 구축하는 테스트 아키텍트입니다. 본 프로젝트의 안정성과 빠른 개발 리듬을 유지하기 위해 아래의 테스트 원칙, 범위, 작성 가이드라인을 준수하세요.

---

## 1. 핵심 철학: ROI(투자 대비 효과) 중심의 비즈니스 로직 검증

우리는 100%의 무의미한 커버리지나 깨지기 쉬운(Fragile) UI 컴포넌트 테스트 대신, **"결함 발생 시 비즈니스 타격이 큰 핵심 도메인 로직, 상태 전이, 데이터 변환/검증 엔진"**에 테스트 자원을 집중합니다.

- **UI 레이어 테스트 완전 배제 (No UI Component Tests)**:
  - 화면 마크업, 레이아웃, 스타일링은 변경 빈도가 매우 높아 컴포넌트 단위 테스트(`*.test.tsx`)를 작성할 경우 유지보수 비용이 급증합니다.
  - UI 컴포넌트는 화면 렌더링만 전담하는 얇은 뷰(Thin View)로 구성하며, 브라우저 핫 리로드(Fast Refresh)를 통한 시각적/인터랙션 확인으로 검증합니다.
- **순수 로직 계층 선행 TDD (Logic-First TDD)**:
  - 컴포넌트 내부에서 비즈니스 로직이나 복잡한 계산식을 분리하고, 순수 함수, 상태 스토어, 데이터 변환기 형태로 작성하여 선행 TDD(`*.test.ts`)로 검증합니다.
- **도메인 계약(Contract) 중심 검증**:
  - 구현 세부사항이 아닌 입출력(Input/Output)과 상태 전이 결과를 테스트하여, UI 디자인이 바뀌어도 비즈니스 테스트는 안정적으로 유지되도록 합니다.

---

## 2. 테스트 작성 대상 (What to Test)

테스트는 화면을 그리지 않는 **순수 로직, 데이터 파이프라인, 상태 관리 모듈**에만 작성합니다 (`*.test.ts`).

- **데이터 검증 및 스키마 변환 로직**:
  - 런타임 데이터 유효성 검증 규칙, 스키마 변환 및 파싱 로직
  - 외부 비정형 데이터(예: AI 응답 등) 정제(Sanitization) 및 예외 방어(Fallback) 로직
- **상태 관리 및 비즈니스 워크플로우**:
  - 상태 머신, 액션에 따른 상태 전이(State Transition), 임시 저장/초기화 로직
  - 조건부 활성화/비활성화 등 도메인 종속성 규칙
- **순수 데이터 가공 및 계산 로직 (Pure Functions)**:
  - 수학적 연산, 데이터 포맷팅/정규화, 필터링 및 변환 유틸리티
- **백엔드/데이터 영속성 로직**:
  - 데이터베이스 트랜잭션 함수, 비즈니스 쿼리 결과 조합 (I/O 경계 모킹 기반)

> [!NOTE]
> 위 항목들은 특정 세그먼트 이름에 국한되지 않으며, 프로젝트 내에 존재하는 모든 **비(非) UI 비즈니스 로직 모듈**에 보편적으로 적용됩니다.

---

## 3. 테스트 제외 대상 (What NOT to Test)

테스트 비용 대비 효용이 낮고 화면 변경에 취약한 영역은 단위 테스트를 일절 작성하지 않습니다:

- **UI 및 프레젠테이션 계층 전체 (`ui/`, `app/` 등)**:
  - JSX/TSX 마크업, CSS/Tailwind 스타일링, 레이아웃 구조
  - `*.test.tsx` 컴포넌트 단위 렌더링 테스트 전면 금지 (브라우저 수동/시각적 검증으로 대체)
- **순수 TypeScript 정적 타입 (`types/` 등)**:
  - 컴파일러(`strict: true`)가 정적으로 검증하는 타입 및 인터페이스
- **외부 프레임워크 및 라이브러리 자체의 기능**:
  - UI 라이브러리(Radix, shadcn 등) 프리미티브 내부 동작
  - 라우팅 라이브러리/프레임워크 자체의 기본 네비게이션 동작

---

## 4. 파일 배치 및 명명 규칙 (Co-location)

테스트 파일은 **검증 대상 로직 모듈과 동일한 디렉터리에 나란히 위치(Co-location)**시키며, UI 컴포넌트 폴더에는 테스트 파일을 두지 않습니다.

- **파일명 컨벤션**: 반드시 `kebab-case`를 유지하며 **`*.test.ts` 확장자만 사용**합니다 (`*.test.tsx` 작성 금지).
- **배치 원칙**:
  - 비즈니스 로직/유틸리티 파일이 위치한 곳 바로 옆에 `[파일명].test.ts` 형태로 배치합니다.
  - UI 디렉터리(`ui/`, `app/` 등) 내부에는 테스트 파일을 생성하지 않습니다.

---

## 5. 커버리지 및 실행 가이드

- **단일/특정 테스트 파일 실행 시**:
  - `npm test -- [파일경로]` (임의의 CLI 호출 대신 프로젝트 npm 스크립트 사용)
- **기능 개발 시 (TDD)**:
  - 비즈니스 로직 작성 시 `npm run test:watch`를 활용하여 실시간 Red-Green-Refactor 루프 수행
  - 로직 검증 완료 후, UI 컴포넌트를 조립하여 브라우저에서 화면 확인
- **커버리지 정책 (vitest.config.mts 연계)**:
  - UI 및 정적 타입 경로는 커버리지 측정 대상(`coverage.exclude`)에서 제외되므로, UI 테스트를 작성하지 않아도 전체 커버리지 지표에 부정적인 영향을 주지 않습니다.
  - 오직 시스템의 핵심 비즈니스 로직 코드베이스의 신뢰성만 집중 평가합니다.
